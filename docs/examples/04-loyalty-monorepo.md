# Example 04 — Loyalty monorepo

How to use the Cursor kit when **Loyalty** is split across three folders. This is **not** generated by `project-foundation-template`.

**Modelo:** misma metodología que un proyecto generado (`cursor/` + `.cursor/` **por repo**). `loyalty-cursor` es el **hub** (producto, full-stack, sync).

## Layout on disk

```text
<workspace>/
├─ loyalty-app-vite/              ← SPA + cursor/ + .cursor/
├─ loyalty-program-serverless/    ← API + cursor/ + .cursor/
└─ loyalty-cursor/                ← Hub: company, full-stack analysis, kit sync
     ├─ kit/                      ← overlays
     ├─ scripts/sync-cursor-layer.mjs
     ├─ analysis/features/<slug>/ ← stories full-stack
     └─ company/future-work/
```

| Package | Cursor layer | Use |
| --- | --- | --- |
| `loyalty-app-vite` | `cursor/` + `.cursor/` | Trabajo solo frontend (`@cursor/prompts/`) |
| `loyalty-program-serverless` | `cursor/` + `.cursor/` | Trabajo solo backend/infra |
| `loyalty-cursor` | hub + `.cursor/` | Backlog, full-stack, `sync-cursor-layer.mjs` |

Refresh app layers after kit changes:

```bash
node loyalty-cursor/scripts/sync-cursor-layer.mjs --target all
```

**Rule:** stack stories live in the app that owns the code. Full-stack stories live in `loyalty-cursor/analysis/features/`. Shipped API/UI docs stay in the app `docs/` after close.

### vs generated project

| Generated (`npm run create`) | Loyalty |
| --- | --- |
| `cursor/` at project root | `loyalty-cursor/` (sibling to apps) |
| `@cursor/prompts/...` | `@loyalty-cursor/prompts/...` |
| Single git repo | `loyalty-cursor` is often its **own** git repo; apps may be separate |

See [`loyalty-cursor/README.md`](../../loyalty-cursor/README.md) and [`docs/cursor-kit-sync.md`](../cursor-kit-sync.md).

---

## Open workspace in Cursor

**Option A — Multi-root (recommended):** add folders `loyalty-app-vite`, `loyalty-program-serverless`, `loyalty-cursor`.

**Option B — Single root:** open `<workspace>/` so `@loyalty-cursor/...` resolves.

Always use **`@cursor/`** when the workspace folder is an app. Use **`@loyalty-cursor/`** for hub / full-stack sessions.

## Example feature — full-stack (redeem with OTP)

**Ticket:** `LOY-456` (JIRA)  
**Feature name:** Redeem points with OTP  
**Feature slug:** `redeem-points-with-otp`  
**Stack scope:** full-stack

### 0. Intake

```text
@loyalty-cursor/prompts/feature/prompt-story-intake.md
@loyalty-cursor/docs/AI-Loyalty-Playbook.md
@loyalty-cursor/docs/documentation-governance.md

Mode: A

Allow members to redeem points only after OTP verification on SMS/email.
Ticket LOY-456. Backend + frontend.
```

Creates:

```text
loyalty-cursor/analysis/features/redeem-points-with-otp/
├── user-story.md
└── feature-manifest.md
```

Optional backlog link in manifest: `Backlog ID: FW-LOY-012`.

### 1. Analysis (backend + frontend context)

```text
@loyalty-cursor/prompts/feature/prompt-feature-analysis-package.md
@loyalty-cursor/projects/loyalty-backend/cursor-rules.md
@loyalty-cursor/projects/loyalty-backend/cursor-rules-api.md
@loyalty-cursor/projects/loyalty-frontend/cursor-rules-frontend.md

Feature slug: redeem-points-with-otp
Feature name: Redeem points with OTP
Ticket/story: LOY-456
Stack scope: full-stack
```

Adds `analysis.md` with impact on Swagger, REGLAS-NEGOCIO, services, MSW.

### 2. Start git branch

From repo where you commit (often `loyalty-cursor`, or monorepo root — match your team):

```bash
node loyalty-cursor/scripts/start-feature.mjs --slug redeem-points-with-otp
```

Branch example: `feature/loy-456`.

### 3. Implement

```text
@loyalty-cursor/prompts/feature/prompt-feature-implementation-package.md
@loyalty-cursor/projects/loyalty-backend/cursor-rules-api.md
@loyalty-cursor/projects/loyalty-frontend/cursor-rules-frontend.md

Feature slug: redeem-points-with-otp
Feature name: Redeem points with OTP
Stack scope: full-stack
```

Touch typical paths:

| Stack | Paths |
| --- | --- |
| Backend | `loyalty-program-serverless/` — handlers, domain, Swagger |
| Frontend | `loyalty-app-vite/src/services/`, `types/`, `mocks/`, `cypress/` |

### 4. Validate

```text
@loyalty-cursor/prompts/feature/prompt-feature-validation-package.md

Feature slug: redeem-points-with-otp
Feature name: Redeem points with OTP
Stack scope: full-stack
```

Run:

```bash
# backend (from loyalty-program-serverless)
npm test

# frontend (from loyalty-app-ui-vite)
npm run lint && npm run build && npm test
# Cypress if UI flow changed
npm run cy:e2e:run
```

Update `test-checklist.md`.

### 5. Review

```text
@loyalty-cursor/prompts/feature/prompt-feature-review.md
@loyalty-cursor/analysis/shared/review-guidelines.md

Feature slug: redeem-points-with-otp
Feature name: Redeem points with OTP
```

Check: Swagger ↔ frontend types ↔ MSW ↔ Cypress aligned.

### 6. GitHub sync (optional)

```powershell
copy loyalty-cursor\scripts\github-story.config.example.json loyalty-cursor\scripts\github-story.config.json
# edit projectOwner, projectNumber, ticketPrefix: LOY

node loyalty-cursor/scripts/sync-github-feature.mjs --slug redeem-points-with-otp
```

### 7. Close

```text
@loyalty-cursor/prompts/feature/prompt-feature-close-package.md

Feature slug: redeem-points-with-otp
Feature name: Redeem points with OTP
```

Updates:

- `loyalty-cursor/analysis/features/INDEX.md`
- `loyalty-cursor/company/future-work/STORY-REGISTRY.md` (if using backlog)
- `loyalty-program-serverless/docs/` — Swagger, REGLAS-NEGOCIO if contract changed
- `loyalty-app-ui-vite/` — services, types, MSW, Cypress if contract changed

## Study before stories (Modo B)

When several JIRA tickets might come from one gap analysis:

```text
@loyalty-cursor/prompts/feature/prompt-story-intake.md
@loyalty-cursor/templates/analysis-study-template.md

Mode: B
Analysis ref: crear

Estudiar gaps en redencion de puntos (OTP, limites, REGLAS-NEGOCIO) antes de abrir LOY tickets.
```

Output: `loyalty-cursor/analysis/studies/redemption-gaps/study.md` with **Candidate stories** → promote `Decision: implement` rows to `analysis/features/`.

## Example: context trace (real feature — LYT-1)

Worked example from the live feature package [`repositorio-puntos-tenant`](../../loyalty-cursor/analysis/features/repositorio-puntos-tenant/) (ticket **LYT-1**, stack **full-stack**, stage **planned**). Use it as a pilot when filling [`context-trace-matrix.md`](../../loyalty-cursor/docs/context-trace-matrix.md).

### Per-feature row (analysis phase)

| Field | Value |
| --- | --- |
| Feature / ticket | LYT-1 — `repositorio-puntos-tenant` — Repo Puntos Tenant |
| Feature type | Full-stack contract + PostgreSQL ledger |
| Folders touched | `loyalty-cursor/analysis/`, `loyalty-cursor/projects/`, (future) `loyalty-program-serverless/`, `loyalty-app-vite/` |
| Files touched | `ANALISIS-REPOSITORIO-PUNTOS-TENANT.md`, `user-story.md`, `analysis.md`, backend/frontend project-context |
| Context read | Deep analysis doc, both project contexts, both cursor-rules, review-guidelines, deferred analysis reversos |
| Context used | `ANALISIS-REPOSITORIO-PUNTOS-TENANT.md`, backend+frontend rules, project-context (patterns only) |
| Decision evidence | PostgreSQL + atomic income debit; separate user vs tenant ledger; purchase idempotency; tenant admin read-only |
| Flow stage | Analysis (package complete; implementation not started) |
| Token value | **High** for analysis doc + rules; **Low** for full context-map or unrelated APIs |
| Recommendation | Scoped pack for “tenant point repository” features (see below) |

### Context trace (paste into `analysis.md` or `implementation-notes.md`)

This block matches what the team already implied in the analysis package; formalize it when implementing:

```markdown
## Context trace

| Context | Used for | Value | Action |
| --- | --- | --- | --- |
| `loyalty-cursor/analysis/backend/ANALISIS-REPOSITORIO-PUNTOS-TENANT.md` | Model, APIs, atomicity, roles | High | Keep scoped — source of truth for LYT-1 |
| `loyalty-cursor/projects/loyalty-backend/cursor-rules-api.md` | API ownership, Swagger, authorizer | High | Keep scoped for backend implement |
| `loyalty-cursor/projects/loyalty-frontend/cursor-rules-frontend.md` | MSW, Cypress, services/types | High | Keep scoped for frontend implement |
| `loyalty-cursor/projects/loyalty-backend/project-context.md` | API list, layers (patterns) | Medium | Read once per backend session |
| `loyalty-cursor/projects/loyalty-frontend/project-context.md` | Pages/components patterns | Medium | Read once per frontend session |
| `loyalty-cursor/analysis/backend/ANALISIS-REVERSOS-AJUSTES-Y-DEVOLUCION-COMPRA.md` | Explicit deferral of reversals | Medium | Conditional — only to confirm out-of-scope |
| `loyalty-cursor/docs/cursor-context-map.md` | Full monorepo map | Low | Do not load by default — too broad |
| Unrelated Swagger files (other APIs) | — | Low | Read only affected `transaction-api` / `admin-api` / `tenant-api` functions |
```

### Aggregated view (after this pilot)

| Context doc | Applies to | Decision value | Default? | Recommendation |
| --- | --- | --- | --- | --- |
| `analysis/backend/ANALISIS-*.md` for the feature | Same slug / epic | High | Scoped | Required when analysis package references it |
| `projects/loyalty-backend/cursor-rules-api.md` | Backend API work | High | Conditional | Required before handler/Swagger changes |
| `projects/loyalty-frontend/cursor-rules-frontend.md` | UI + contract consumer | High | Conditional | Required when MSW/Cypress involved |
| Deferred `ANALISIS-REVERSOS-*` | LYT-1 scope boundary | Medium | No | Read only to avoid scope creep |
| Entire `cursor-context-map.md` | Any | Low | No | Link from session prompt instead |

### Session prompt — backend implementation (LYT-1)

When moving from **planned** to **implementation**, start a fresh chat:

```text
Loyalty — LYT-1 — backend implement (tenant point repository)

Read ONLY:
- loyalty-cursor/analysis/features/repositorio-puntos-tenant/user-story.md
- loyalty-cursor/analysis/features/repositorio-puntos-tenant/analysis.md
- loyalty-cursor/projects/loyalty-backend/cursor-rules.md
- loyalty-cursor/projects/loyalty-backend/cursor-rules-api.md
- loyalty-cursor/analysis/backend/ANALISIS-REPOSITORIO-PUNTOS-TENANT.md
- loyalty-program-serverless/transaction-api/ (income path)
- loyalty-program-serverless/admin-api/ (purchase, balance, history)

Do NOT read: loyalty-app-vite/, ANALISIS-REVERSOS-*, full Swagger tree, cursor-context-map.

Task: PostgreSQL migration + ledger service + atomic income debit (step 1–4 from analysis recommendation).
```

### Session prompt — frontend (after Swagger frozen)

```text
Loyalty — LYT-1 — frontend implement

Read ONLY:
- loyalty-cursor/analysis/features/repositorio-puntos-tenant/user-story.md
- loyalty-cursor/projects/loyalty-frontend/cursor-rules-frontend.md
- loyalty-program-serverless/docs/api/ (purchase, balance, history endpoints only)
- loyalty-app-vite/src/pages/ProgramAdministration/
- loyalty-app-vite/src/pages/Administration/

Do NOT read: full backend codebase, unrelated program APIs.

Task: services/types + MSW + ProgramAdministration purchase + tenant read-only history.
```

### Pilot routing rule (full-stack inventory — Loyalty)

**Maturity: Pilot** (LYT-1 only — confirm with 2–3 more stories before “Area” level)

**Required:**

- Feature package under `loyalty-cursor/analysis/features/repositorio-puntos-tenant/`
- Matching `loyalty-cursor/analysis/backend/ANALISIS-<topic>.md` when it exists
- Backend rules + affected API folders in `loyalty-program-serverless`
- Frontend rules + affected pages/services when UI is in scope

**Conditional:**

- `ANALISIS-REVERSOS-*` or other deferred docs — scope boundary only
- `loyalty-app-vite/docs/testing/GUIA-ALINEACION-E2E-SWAGGER-FRONTEND.md` — when contracts change

**Do not read by default:**

- Full monorepo context map
- Swagger for APIs not in TARGET SCOPE
- Frontend MSW handlers for unrelated domains

Copy this rule into [`context-trace-matrix.md`](../../loyalty-cursor/docs/context-trace-matrix.md) after the next full-stack feature confirms or adjusts it.

## Sync kit from foundation template

1. Land generic changes in `project-foundation-template`.
2. From `loyalty-cursor/`: `node scripts/sync-cursor-layer.mjs --target all` (copies foundation + overlays into both apps and refreshes hub Capa C2).
3. Do **not** overwrite `analysis/features/<slug>/` with real content (the script preserves those folders).
