# AI with Cursor — de qué va el curso

Versión con inicio, fin, contexto del agente y pre-requisitos explicados: [course-overview-detailed.md](course-overview-detailed.md) · [PDF](course-overview-detailed.pdf).

Seis clases de 90 minutos, una detrás de otra. Cada persona trae **su repositorio real** y sale sabiendo usar IA para programar con alcance, memoria y verificación.

No es un curso de trucos de Cursor. Es entender **cómo funciona un modelo** cuando escribe código, y dejar hábitos y archivos para que no se invente el repo. Cursor es el laboratorio. Las mismas ideas valen en Copilot, Claude u otra herramienta.

No promete “diez veces más rápido”. Promete menos retrabajo, menos contexto perdido entre chats y cambios más chicos.

## Para quién

Desarrolladores que ya mantienen un producto y quieren usar IA sin perder el control del código.

No es para arrancar un proyecto desde cero.

## Cómo es una clase

| | |
| --- | --- |
| Duración | 90 minutos |
| Sesiones | 6, en bloque seguido |
| Tareas entre clases | Ninguna. Todo se entrega en esa sesión |
| Grupo | 4 personas |
| Idioma | Se habla en español. Lo que se guarda en el repo va en inglés |
| Práctica | En el repo de cada quien, no en un ejemplo vacío |

Cada clase: explicación corta, práctica en el teclado, cierre con un resultado concreto.

## Las seis sesiones

| Sesión | Tema | Con qué te vas |
| --- | --- | --- |
| 1 | Cómo piensa un modelo | Un cambio chico, con archivos acotados y una prueba corrida |
| 2 | Mapa del repo | Un mapa y reglas para que la IA no invente carpetas |
| 3 | Memoria de una historia | La historia escrita en archivos: qué entra, qué no, y cómo probarla. **Sin código** |
| 4 | Implementar y validar | El cambio mínimo del ticket, revisado y verificado por ti |
| 5 | Revisar y cerrar | Review, cierre y el hábito de un chat nuevo por fase |
| 6 | Visión de producto | Una página de visión, tres ideas de backlog y un checklist para el día a día |

Al final cada persona recorrió **una historia real** de punta a punta: definir → analizar → implementar → validar → revisar → cerrar.

## Tres ideas que se llevan el primer día

1. El modelo **no conoce** tu repo. Solo ve lo que le pasas en esa petición.
2. El chat **no recuerda** el chat de ayer. Lo que debe durar vive en git.
3. El humano **verifica**. Una respuesta segura puede ser falsa.

## Qué necesitas antes del primer día

- Cursor instalado (u otra herramienta de IA que ya uses) y **tu repo abierto**.
- Permiso para crear una rama y hacer commit.
- Un ticket o bug pequeño, de 1–2 días, acordado con tu lead.
- El comando con el que prueban hoy ese repo (test, lint o el paso manual equivalente).

## Qué no incluye

- Crear un proyecto nuevo.
- Copiar la carpeta de otro producto.
- Tareas para la casa entre sesiones.
